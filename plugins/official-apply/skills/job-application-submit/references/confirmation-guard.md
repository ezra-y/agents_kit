# 提交批准与程序闸门

## 两阶段调用

第一次调用只检查：

```text
apply.submit { runId }
```

检查通过后返回：

```text
dryRun: true
approval:
  approvalId
  approvalToken
  expiresAt
  summary
```

`summary` 只保存任务、页面、按钮和材料引用，不保存简历正文或用户答案。向用户展示可读摘要，
批准令牌只在当前运行中临时持有，不写入公共文档或证据。

用户通过后续消息确认摘要，或专用“确认投递”勾选对应的展示摘要与本次摘要一致后执行：

```text
apply.submit {
  runId,
  confirm: true,
  approvalToken
}
```

## 令牌为何会失效

程序把令牌绑定到：

- `taskId` 和 `runId`
- 规范化岗位页面 URL
- 提交幂等键
- 当前页面控件数量
- 当前页面填写值摘要

页面或填写内容变化后，旧令牌失效。重新执行提交前检查时，同一运行中先前未使用的令牌也会
失效。令牌默认 30 分钟过期，消费后不能重用。

数据库只保存令牌的 SHA-256 摘要。最终提交尝试会记录同一摘要，便于事后确认本次提交确实
经过了哪次检查，但无法从数据库恢复原令牌。

## 用户确认层

程序闸门负责防止单次调用、旧页面、错任务和重复提交。它不读取聊天或表格，因此 Agent 仍需做到：

1. 先展示本次实际提交内容。
2. 接受用户后续消息，或读取第二张表中用户亲自勾选的专用“确认投递”。
3. 确认授权对应同一岗位和同一份展示摘要后使用令牌。

表格授权匹配时无需再等聊天确认。普通复选框、AI 代勾、摘要不一致或含糊讨论都不构成授权。
当前没有表格监听器；必须有 Agent 主动读取勾选并调用 `apply.submit`。

## 批量申请

用户已明确授权某份来源和选择规则内的岗位真实投递，并指定使用已核对的资料时，这份批次委托可作为最终授权。先展示本批来源、处理条件和材料摘要，然后逐条预检、逐条消费令牌，不重复索要同一授权。仅说填写、登录、处理验证码不构成批次提交委托。

没有这类明确委托时，先为已准备任务展示清单，用户一次确认可以批准清单中全部岗位。

某条任务在确认后发生变化时，只重新检查该条；不能静默替换成另一岗位。某条结果不确定时，
锁定该条且不重试，不影响其他已明确批准且尚未变化的任务。

## 站点确认弹窗

有些网站先点击“提交”，再出现站点自己的确认弹窗。站点 PageScript 或提交执行器应把这两步
封装成一次逻辑提交：

- 写入提交尝试和消费批准令牌后，才允许点击第一步。
- 第二步只处理同一次站点确认，不重新签发令牌。
- 任一步结果不确定都进入 `submission_uncertain`。
- 普通 Agent 不直接绕过执行器操作弹窗。
