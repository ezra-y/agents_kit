# 招聘来源和候选岗位记录

第一张表记录招聘来源和本次公司范围。它帮助用户决定处理哪些公司，不代表排除其他来源，也不代表
批准填写或投递。

第二张表同时承载已保存的站内简历结果与官网具体岗位。保存公司简历后即写入公司、简历入口、填写状态和检查结果；尚无具体岗位时岗位/JD留空，不能省略这条结果。找到具体岗位后记录其真实链接，并在同一行继续跟踪该岗位：

```text
公司、岗位、岗位链接、完整 JD、来源、信息状态、用户选择、材料摘要、确认投递、检查结果、填写状态、提交状态
```

填写站内简历后，只有用户已授权按其求职意向查看岗位时，才只读收集官网展示的具体推荐岗位、
岗位链接和完整 JD（职位说明）。保留页面或接口来源。JD 缺失、截断或只有摘要时标为“待核实”，
不根据公司行业或岗位名称替用户排除。

新候选的用户选择默认为“待决定”。把候选岗位交给用户选择“准备投递”“再看看”或“不考虑”。
“准备投递”仍需填写校验、实际提交摘要和后续确认。官网确认成功后才记为“已提交”。

“确认投递”是专用最终授权。只有该行已展示具体公司、岗位、城市、材料和志愿顺序，且用户亲自
勾选后才生效。AI 不勾选这个字段。公司范围、验证码、处理状态或普通复选框仍只表示各自用途。
读取勾选后，按提交 Skill 重新预检；实际摘要与该行展示摘要一致时可以提交，不再索要聊天确认。
摘要变化时停止，更新展示后等待用户重新确认。

官网原文、检查结果和用户选择分别记录。重新采集同一岗位时更新官网原文与检查结果，保留已有用户
选择、填写进度和提交进度。同一岗位始终更新第二张表的原行，不复制到第三张表。

两张表的位置统一登记在私有数据目录的 `tables/locations.json`。首次查找、登记已有文件/链接、创建空本地表或飞书表、逐行回写的实际工具步骤见
[表格位置与创建](../../recruitment-link/references/table-setup.md)。没有招聘来源时，按 recruitment-link 的搜索步骤获取一小批，不能反复要求用户提供不存在的表。

用户没有选展示方式时先询问一次。已有表就复用，创建成功后登记位置。完成填写、独审或提交后，按批次保存的原表/原行身份写回并读回确认；不能因当前默认位置改变而把旧结果写到新表。
当前的文件和飞书读写由活跃 Agent 调用工具执行。`apply.submit` 本身不读取表格，也没有后台同步或勾选监听；没有活跃任务时勾选会停在表里等待处理。

每家公司完成后的两表写入顺序见 [表格筛选与收尾](../../recruitment-link/references/fill-selection.md)。第二张表写回成功后，再按独审结果更新第一张表的处理完成；两者都不等于真实投递。
