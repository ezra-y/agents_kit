# 岗位推荐

把范围内适合用户的具体岗位尽量找全，交付便于比较、阅读和选择的飞书云文档；表格保存同一份信息供 AI 执行。命令在插件根目录运行，私有资料使用配置中的 `dataRoot`。

## 1. 读取已有资料

读取最新简历、`preferences.json` 中的 `jobRecommendation`、原有公司范围与 `tables/locations.json`。继续已有批次时读取 `recommendations/<batchId>/batch.json`，复用其文档和原表位置。缺少影响判断的偏好时集中询问，已有资料直接复用。

个人偏好只保存在私有目录。用户新增方向或调整数量后，更新偏好再处理岗位。

## 2. 收集与排序

核实官网岗位列表及完整职责、要求，保留官网岗位链接、来源和核实时间。收集包含分页的实际授权范围；公开页面直接读取，需要登录时复用 recruitment-session。旧推荐重新检查。

结合用户偏好、简历经历和职位要求，逐个判断岗位，给出 0～100 的适配度并排序。分数表达匹配程度；明确不满足的申请条件不能靠分数掩盖，资料不足的岗位标记待核实。相关性相近时优先有简历经历支持的岗位。

同类多个合适岗位一并保留；数量根据实际结果确定，0～5 个作为参考，可超过五个。按官网职位 ID 或完整岗位链接去重，名称相同但城市、团队或职位编号不同的岗位分别保留。展示具体岗位和适配度，推荐理由留在判断过程中。

同时核实每家公司的投递名额、志愿顺序要求和已有申请。未知限制保留未知，不能写成不限；进入申请前从官网确认。

## 3. 生成一致的表格与云文档

按 [数据与工具](references/data-and-tools.md) 保存一个批次文件。先执行 `validate`，再从它生成表格记录和文档草稿。

表格每个具体岗位一行。复用原候选表，按准确岗位链接更新原记录；原公司汇总行保留，拆出的岗位单独关联，避免把公司填写完成当作某个岗位已提交。必要字段按原表实际列名映射。

使用 lark-doc 创建或编辑云文档。按公司组织，展示投递数量与排序后的岗位；保留完整 JD，短信息选择便于比较的排版。地点、薪资、届别、截止日期以实际资料为准，官网链接可附在岗位名上。每个岗位保留独立的确认行。批次使用的简历和志愿顺序规则在文档开头简短说明。

原生勾选“确认投递”或将对应确认行文字改为“投递”，表示用户选择该具体岗位。确认行由用户操作。创建后 fetch 完整文档并 `bind`，保存真实文档块与岗位之间的关联；表格写回后读回字段，文档核对完整 JD。

更新文档先 `fetch` 和 `choices` 读取用户最新选择，再按块更新岗位事实和状态，保留确认块 ID。重新排序移动原块；岗位、城市或材料变化时展示新摘要，局部创建新的未勾选确认块并再次 `bind`，保留旧绑定证据，等待用户重新确认。新增岗位也按未勾选项增量绑定。

## 4. 读取选择并继续

按 [文档选择与自动处理](references/document-selection.md) 获取最新文档，执行 `choices`。将返回的选择同步到原表并读回。表格中的确认字段由 AI 镜像维护；本流程的授权来源是绑定文档中的用户选择。

选中岗位分别复用或创建独立任务，保存原表行身份、岗位链接、材料和文档确认来源，再交给 job-application-submit。批次材料已展示且用户确认后，沿用现有填写、审查和提交预检；发生内容变化时重新确认。官网申请结果决定已提交、未提交或结果不确定的状态。

需要持续自动处理时，使用宿主已有的定时任务能力保存该批次的检查任务，成功后登记任务编号。没有新选择或需用户处理的问题时保持安静。每次恢复先读批次与真实申请状态，避免重复投递。

交付文档链接、表格位置、公司和岗位数量，以及实际需要用户处理的项目；自动检查只有真实创建成功后才说明已启用。
