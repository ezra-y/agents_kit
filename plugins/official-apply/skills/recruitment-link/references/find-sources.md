# 用户没有招聘来源时

## 1. 先复用意向

读取已保存的目标职责、校招/社招/实习类型、毕业时间及用户明确的地区限制。仅补影响本轮搜索的缺项，已有信息不重问。
用户表示没有来源并希望助手开始寻找时，直接做只读搜索；这不授权填写或投递。不要把“没招聘表”继续作为阻塞。
用户只给了一个官网让你填写时，仍保持这一家公司范围，不因此额外搜十家公司。

## 2. 使用实际可用的搜索和网页工具

先检查当前宿主的工具列表。使用网页搜索工具提交“目标职责＋招聘类型＋届别/年份”的组合；搜索关键词来自用户事实，避免默认所有人都是同届校招。
例如用户明确找 AI 产品校招时，查询“AI 产品经理 目标届别 校园招聘”“Agent 产品经理 校招 官方招聘”。拿到企业名后用企业官方招聘域名缩小搜索。
当前环境有 agent-reach 时读取其 search/career 参考，按可用后端调用；没有它时使用宿主自带搜索工具。它不是插件必装依赖。
只有用户明确找最新秋招且已安装 qiuzhao-feed 时才读取其 Skill，按 source-routing 使用其输出；普通社招/实习搜索不依赖秋招数据源。

搜索工具返回结果后，用网页读取工具打开实际官网公告/岗位详情。动态页面需浏览器时读取当前浏览器工具说明，复用已有会话；不靠搜索摘要判定开放、学历要求或 JD 全文。
先得到一批最多 10 条可展示的来源；用户要求更多后再扩大。没有可靠结果时报告实际已查范围与缺口，不编造公司或岗位凑数。

## 3. 分类与核实

逐条记录：公司、真实来源链接、招聘方向、地区、招聘类型、明确条件、页面更新时间或“未标注”、本次检查结果。
聚合公告保留为招聘来源，不能把“产品等多个方向”当成已发现 AI 产品经理的具体岗位。具体岗位保存独立链接和完整 JD。
缺 JD、条件不清或官网无法访问的记录写“待核实”；开放状态只有官网当前证据才能确认。用户尚未确定取舍时保留选择为“待决定”。
同一网址再次发现时更新原记录，不重复新增。不同岗位即使名称相同也保留各自的真实岗位链接。

## 4. 写表并展示

按 table-setup 第 4 节，将来源写到 sources 表；需要保留明确具体岗位时写 candidates 表。使用实际列映射，不把内部任务编号展示成用户需要填写的字段。
写入后按第 5 节读回核对，告诉用户表格位置、已找到的数量和需要确认的条件。没有表格时先完成创建与登记，再写入。
用户选择后才将选中范围导入执行任务；搜索结果不会自动勾选确认投递。
