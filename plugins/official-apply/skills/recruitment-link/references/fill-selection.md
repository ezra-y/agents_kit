# 继续填写：先选行，再补空，最后写两张表

## 1. 从当前表格产生清单

本流程用于用户要求继续处理未完成网申的场景。历史任务库只用于关联记录及排除已有结果，不能作为待填写范围来源；历史登录成功也不是选公司依据。
先用 table-locations.py show 取得 sources、candidates。第一张表的 fieldMap 要明确“处理完成”“填写状态”“提交状态”“公司”“来源链接”；飞书使用真实字段 ID。不同用户实际列名不同，不把某个复选框名称硬编码为所有人的字段。

飞书用 `lark-cli base +record-list --as user --base-token <base> --table-id <table> --offset <offset> --limit 200 --format json`，按这些字段的真实 ID 重复传 --field-id（去重）；根据 has_more 读取所有页，把各页原始 JSON 信封数组存为本次私有 source-rows.json。
只读清单命令：

```bash
python3 skills/recruitment-link/scripts/plan-fill.py --data-root <dataRoot> --rows <source-rows.json>
```

输出 items 中只有 decision=eligible 可以进入网页；skipped 表示已处理或已有结果，blocked 表示需要核实。不要把返回 ok:true 当成所有行都可以填写。
程序排除已勾完成、表内已投递/流程已推进、已保存/已填写，以及原行或精确公司名关联的本地已完成/已投递/结果不确定记录；提交尝试表里的成功或未决结果优先于过时的任务状态。未知勾选值、字段缺失、缺少后续页不会放行。旧行身份带岗位后缀时按原行 ID 关联，不通过品牌别名猜公司。
同公司已有完成记录时默认保守跳过；用户明确要求更新该公司的特定简历时，另建明确范围的更新任务，不能悄悄取消原投递记录。

本地 CSV 用 read-local 读取当前 rows：按实际配置列应用同样条件，只保留完成勾选为空/false且填写状态未完成、无已投递证据的行。plan-fill 当前仅解析飞书矩阵，不把 CSV 强行传给它；缺少状态列时先核实列映射，不自行当作未完成。
字段模板中的“填写完成”是处理完成标记；“确认投递”是独立的用户授权，两者用途不同。

## 2. 每家公司打开前再次核实

已选中飞书行时，先用 `+record-get --as user --base-token <base> --table-id <table> --record-id <rowId> --format json` 读取这行最新值，再把这个信封交 plan-fill 复查。
完整清单之后用户可能改了勾选；实时检查通过才打开对应官网。本地文件则重读该行。新读回与旧清单不一致时以最新值为准。
将 eligible 行关联的 taskId/runId 交给 recruitment-session，每次在当前页面重新 inspect 登录；已有 Cookie 文件、上次登录报告和旧 run 状态只作恢复线索。
页面上先辨认已填栏目与空白字段，只补空白。网页已有内容与用户资料不一致时报告差异，不默认覆盖；用户明确要求修正的字段才按新授权修改。
fillMode=empty_only 是范围要求，当前 apply.fill_page 不接收这个参数。整页适配器不能保留既有字段时，使用宿主浏览器工具逐字段补空；结构化局部写入失败时按填写 Skill 转 Computer Use；视觉路径仍失败且能力演进诊断后才记录具体阻塞，不盲调整页填写。

## 3. 保存之后必须完成两表记录

### 3.1 立即保存到第二张表

官网保存后重新打开并读回。确认保存成功后，按 table-setup 的 record-upsert 或本地工具写入 candidates 结果表：公司、简历入口、填写状态、登录方式、检查结果和实际检查时间。
登录方式使用登录阶段交接的手机/邮箱/其他；仅复用会话且无依据时记“未确认”，不覆盖同账号已有的已确认方式。保留用户原有结果，不存手机号、邮箱地址、密码或验证码。结果表缺列时先按 table-setup 补列并登记真实字段 ID，再写回。
没有具体岗位也要保留公司简历结果；岗位、岗位链接、JD 保持空，不能为了落表编造“通用岗位”。有真实候选岗位时再记录其岗位链接与完整 JD。
飞书公司简历行通过公司+简历入口确定，具体岗位行通过真实岗位链接确定。先查询，再按真实 recordId 更新；新增后立即记下返回 ID。对于本地结果表，公司简历行由文件工具按公司+简历入口更新，不把简历 URL 填到岗位链接列以迁就 keyField。
只传本次变化字段，保留用户选择、真实投递状态和旧备注。保存成功但独审未执行，填写状态写“已保存”，检查结果说明“独审待执行”；没有保存成功的记录写“部分填写/未填写”及具体阻塞，不能报完成。
调用 record-get/read-local 或文件工具读回结果表真实行。把该表、recordId/键、taskId、源行身份保存在本批 table-setup 所述绑定文件中。

### 3.2 再更新第一张表

第二张表读回成功后，第一张表写“已保存/部分填写”等真实填写状态；先不勾完成。
按 resume-fill-review 每10家/尾批的独立审查流程执行。独审通过后先更新第二张表同一行，再把第一张表填写状态设为独审通过、处理完成设为 true；分别读回确认。
有必填缺项、未解决的内容差异或表格写回失败时，完成复选框保持未勾，并记录未完成的栏目/字段。只填写不改成已投递，也不改专用确认投递勾选。
下次继续时，已保存但待审的行只补独审或表格同步，不重新填写官网。新的修复授权只处理明确的差异字段。

### 3.3 结束条件

一家公司只有“官网保存读回 + 独审 + 第二张表记录读回 + 第一张表更新读回”都完成，才报告本次填写任务完成。
不能完成表二登记或写入时，本地保留已有证据，状态写“表格待同步”；继续处理其他可执行项，但结束报告列出未同步记录。
这条链由活跃 Agent 调用工具；当前没有后台监听、自动调度或跨工具不可绕过的强制执行器，不能声称单凭 Skill 文本能保证模型永远遵循。
