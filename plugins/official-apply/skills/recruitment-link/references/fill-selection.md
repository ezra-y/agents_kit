# 继续填写：先选行，再补空，最后更新原记录

## 1. 从当前表格产生清单

本流程用于用户要求继续处理未完成网申的场景。历史任务库只用于关联记录及排除已有结果，不能作为待填写范围来源；历史登录成功也不是选公司依据。
先用 table-locations.py show 取得 sources、candidates。来源位置的 fieldMap 要明确“填写状态”“提交状态”“公司”“来源链接”，并按实际用途登记“投递情况”或“处理完成”复选框；飞书使用真实字段 ID。不同用户实际列名不同，不把某个复选框名称硬编码为所有人的字段。

飞书用 `lark-cli base +record-list --as user --base-token <base> --table-id <table> --offset <offset> --limit 200 --format json`，按这些字段的真实 ID 重复传 --field-id（去重）；根据 has_more 读取所有页，把各页原始 JSON 信封数组存为本次私有 source-rows.json。
只读清单命令：

```bash
python3 skills/recruitment-link/scripts/plan-fill.py --data-root <dataRoot> --rows <source-rows.json>
```

输出 items 中只有 decision=eligible 可以进入网页；skipped 表示已处理或已有结果，blocked 表示需要核实。不要把返回 ok:true 当成所有行都可以填写。
程序排除投递情况或处理完成已勾选、表内已投递/流程已推进、已保存/已填写，以及原行或精确公司名关联的本地已完成/已投递/结果不确定记录；提交尝试表里的成功或未决结果优先于过时的任务状态。未知勾选值、字段缺失、缺少后续页不会放行。旧行身份带岗位后缀时按原行 ID 关联，不通过品牌别名猜公司。
同公司已有完成记录时默认保守跳过；用户明确要求更新该公司的特定简历时，另建明确范围的更新任务，不能悄悄取消原投递记录。

本地 CSV 用 read-local 读取当前 rows：按实际配置列应用同样条件，只保留完成勾选为空/false且填写状态未完成、无已投递证据的行。plan-fill 当前仅解析飞书矩阵，不把 CSV 强行传给它；缺少状态列时先核实列映射，不自行当作未完成。
字段模板中的“填写完成”是处理完成标记；“确认投递”是独立的用户授权，两者用途不同。

## 2. 每家公司打开前再次核实

已选中飞书行时，先用 `+record-get --as user --base-token <base> --table-id <table> --record-id <rowId> --format json` 读取这行最新值，再把这个信封交 plan-fill 复查。
完整清单之后用户可能改了勾选；实时检查通过才打开对应官网。本地文件则重读该行。新读回与旧清单不一致时以最新值为准。
将 eligible 行关联的 taskId/runId 交给 recruitment-session，每次在当前页面重新 inspect 登录；已有 Cookie 文件、上次登录报告和旧 run 状态只作恢复线索。
页面上先辨认已填栏目与空白字段，只补空白。网页已有内容与用户资料不一致时报告差异，不默认覆盖；用户明确要求修正的字段才按新授权修改。
fillMode=empty_only 是范围要求，当前 apply.fill_page 不接收这个参数。整页适配器不能保留既有字段时，使用宿主浏览器工具逐字段补空；结构化局部写入失败时按填写 Skill 转 Computer Use；视觉路径仍失败且能力演进诊断后才记录具体阻塞，不盲调整页填写。

## 3. 更新用户的结果位置

先读 locations.json。sources 和 candidates 可以是同一数据表的不同视图；tableId 相同时更新原 recordId 一次，靠视图筛选显示结果，不创建副本。不同数据表才分别更新来源行和结果行。不能凭“第二张表”的顺序判断目标。

官网保存后重新打开并读回，再记录真实填写状态。填写状态与投递情况独立：保存简历不勾投递，真实投递才更新投递情况。只有实际登记了“处理完成”字段时才按其含义更新；不要用投递复选框代替。

优先沿用用户列名和选项。常用状态为未填写、填写中、部分填写、已填写、暂时无法填写。完整检查证据保存在本地，面向用户的阻塞原因只写一两句话；通过检查的记录不重复写检查过程。除非用户要求，不自动补登录方式、检查时间等展示列。

推荐岗位使用实际岗位名称，岗位链接使用对应职位地址；没有具体岗位时保留现有招聘入口，不把简历编辑地址当成岗位链接，也不编造岗位。需要用户确认的暂选信息单独写入“不确定信息”。

按 resume-fill-review 的批次独立审查流程执行，内部审查结果与用户展示列分开。写回后读回同一记录的变化字段，保存原行身份和结果位置。表格更新失败时保留本地证据，记录待同步；不要重复填写已经保存的官网内容。

一家公司须完成官网保存读回、独立审查及实际结果记录读回，才报告本次填写任务完成。网站限制或内容差异未解决时如实保留部分填写状态。
