# 继续填写：先选行，再补空，最后更新原记录

## 1. 从当前表格产生清单

本流程用于用户要求继续处理未完成网申的场景。历史任务库只用于关联记录及排除已有结果，不能作为待填写范围来源；历史登录成功也不是选公司依据。
先用 table-locations.py show 取得 sources、candidates。来源位置的 fieldMap 要明确“填写状态”“提交状态”“公司”“来源链接”，并按实际用途登记“投递情况”或“处理完成”复选框；飞书使用真实字段 ID。不同用户实际列名不同，不把某个复选框名称硬编码为所有人的字段。

飞书用 `lark-cli base +record-list --as user --base-token <base> --table-id <table> --offset <offset> --limit 200 --format json`，按这些字段的真实 ID 重复传 --field-id（去重）；根据 has_more 读取所有页，把各页原始 JSON 信封数组存为本次私有 source-rows.json。
只读清单命令（登记了独立 candidates 表时必须同时传两张表的完整快照）：

```bash
python3 skills/recruitment-link/scripts/plan-fill.py \
  --data-root <dataRoot> \
  --rows <source-rows.json> \
  --candidate-rows <candidates-rows.json>
```

如果 sources 和 candidates 的 `baseToken`、`tableId` 都相同，可以复用同一份快照；登记了不同的
`baseToken` 或 `tableId` 却没有传 `--candidate-rows` 时命令报错，不能默默只查来源表。候选表不要求
存在“提交状态”列，只按实际 fieldMap 读取“公司”“填写状态”“投递情况”。

输出 items 中只有 decision=eligible 可以进入网页；skipped 表示已处理或已有结果，blocked 表示需要核实。不要把返回 ok:true 当成所有行都可以填写。
程序排除投递情况或处理完成已勾选、表内已投递/流程已推进、已保存/已填写，以及原行或精确公司名关联的本地已完成/已投递/结果不确定记录；提交尝试表里的成功或未决结果优先于过时的任务状态。候选表逐行读取，任一精确同名候选行已完成填写或已投递就跳过来源行；部分填写、暂时无法填写仍可继续重试。`source-result-map.json` 只有在 baseToken 同时匹配 sources 与 candidates、且 sources tableId、candidates tableId 全部匹配时，才按其 source recordId 到 candidate recordId 的关联补充判断。未知相近名称不模糊合并，也不创建别名框架。未知勾选值、字段缺失、缺少后续页不会放行。旧行身份带岗位后缀时按原行 ID 关联。
同公司已有完成记录时默认保守跳过；用户明确要求更新该公司的特定简历时，另建明确范围的更新任务，不能悄悄取消原投递记录。

本地 CSV 用 read-local 读取当前 rows：按实际配置列应用同样条件，只保留完成勾选为空/false且填写状态未完成、无已投递证据的行。plan-fill 当前仅解析飞书矩阵，不把 CSV 强行传给它；缺少状态列时先核实列映射，不自行当作未完成。
字段模板中的“填写完成”是处理完成标记；“确认投递”是独立的用户授权，两者用途不同。

## 2. 按批前固定清单执行

主控在派发前一次完成源表、结果表和已有映射的核对，将已经确认的公司别名归入同一处理记录，排除任一对应记录已填写或已投递的公司。未经核实的相近名称不自动合并。将最终eligible名单固定到本批index后派发。
填写者直接执行分配的清单，不逐家公司再次读取整表、查重或重复运行筛选。用户明确改变本批名单或资料时，主控只调整受影响条目；没有新指令时沿用批前结果。
将 eligible 行关联的 taskId/runId 交给 recruitment-session，每次在当前页面重新 inspect 登录；已有 Cookie 文件、上次登录报告和旧 run 状态只作恢复线索。
页面上先辨认已填栏目与空白字段，只补空白。网页已有内容与用户资料不一致时报告差异，不默认覆盖；用户明确要求修正的字段才按新授权修改。
fillMode=empty_only 是范围要求，当前 apply.fill_page 不接收这个参数。整页适配器不能保留既有字段时，使用宿主浏览器工具逐字段补空；结构化局部写入失败时按填写 Skill 转 Computer Use；视觉路径仍失败且能力演进诊断后才记录具体阻塞，不盲调整页填写。

## 3. 更新用户的结果位置

本节统一规定结果同步；文件和飞书的写入命令见 [原表回写](table-setup.md#5-将执行结果写回原行)。先读 locations.json 和本批原行绑定。sources 与 candidates 的 tableId 相同时只更新原 recordId 一次；不同时先更新具体岗位行，再更新来源公司的汇总行。

### 更新时机与负责人

每次出现以下结果，先保存对应证据，再同步受影响的原行并读回：

- 官网保存并重新打开核对完成，或独立审查、返修改变了已确认的填写范围。
- 新增或解决了登录、验证码、页面操作、材料、个人资料或名额问题。
- 用户补充资料、改变岗位选择或志愿，使原状态或待办发生变化。
- 提交得到成功、明确未提交或结果待核实的结论；后续官网核实改变结论时再次同步。

单独执行时由执行者写回；并行执行时由主控指定一个表格写入者。各执行者交回原行 ID、结果和证据位置，写入者收到后可合并同轮更新，最迟在下一次对用户汇报进度或交接前完成。其他公司的填写与修复继续进行，表格同步不等待整批返修结束。

### 各列记录什么

沿用用户已有列名和选项，只更新有新证据的字段。

| 内容 | 更新规则 |
| --- | --- |
| 填写状态、填写进度 | 保存读回只证明已保存范围一致。完整校验通过或该岗位已确认提交，才标该岗位填写完成；部分填写且比例无法核实时留空，不根据读回字段数量估算百分比。 |
| 投递情况、提交状态 | 具体岗位只有确认提交成功才勾选；结果未决保持待核实。成功依据保留在提交状态的简短说明中，详细回执留在本地证据。 |
| 公司汇总、检查结果 | 写明已选岗位中成功、待核实和尚未提交的数量。公司已有投递的勾选不表示其他岗位完成；汇总变化时替换过时的“仅保存、未投递”等当前状态说明。 |
| 阻塞原因 | 只写当前阻碍下一步的原因及动作，控制在一两句话。问题解决后移除对应旧原因；已确认成功的岗位清空此列。 |
| 不确定信息 | 列出仍需本人补充或确认的具体资料，以及仍有效的暂填值。已回答的问题及时移除；程序故障写入阻塞原因。 |

推荐岗位使用真实岗位名称，岗位链接使用对应职位地址；没有具体岗位时保留招聘入口。处理完成标记和用户确认投递字段继续按各自用途使用。已接受的不确定项、已核实官网限制及其他岗位的未完成内容分别保留，不因单个岗位成功改写整家公司所有记录。

### 同步完成条件

同一批写入完成后，重新读取变化字段，确认两表与本地结果一致，再记录本次同步完成。每批结束或中断交接前检查是否还有未同步结果。写入失败时在原批次记录保留“表格待同步”、原行 ID、待写结果和证据；恢复后优先补同步，无需重新填写已保存的官网内容。完整检查过程留在本地，表格只展示当前结果和待办。
