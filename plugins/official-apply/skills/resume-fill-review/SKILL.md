# resume-fill-review

输入为 `taskId`、`runId`、`batchId`、`resumeUrl` 和本次处理范围。按下面顺序执行；调用示例中的值替换为本次真实值。
命令在插件根目录执行；先读配置中的私有数据绝对目录。下文 `<dataRoot>` 指该目录，所有证据都保存在其中。
`task run` 是旧的一键页面执行入口，不包含下面的表格选行、表二收尾和独立审查，不能用它替代本流程。当前宿主未提供 apply 工具时，使用可用浏览器工具逐步完成相同动作与读回；缺少某步能力要说明，不能跳过。

## 批次执行合同

用户限制模型调用时优先遵守：不另调模型、不把资料交给其他执行器；由当前主控审查原始资料与真实读回，注明审查方式，不声称另一个独立会话已通过。

批量任务默认10家公司为一批；用户指定同一轮统一处理时按用户给定名单，复用 `<dataRoot>/reviews/<batchId>/index.json`。批前记录本批名单和固定工具版本；由主控统一维护批次阶段，填写者只交回各公司结果。
固定顺序为 `filling → reviewing → repairing → closed`：10家公司首次处理结果全部齐全后，派一次 Sol 审查（用户指定 Terra 时使用 Terra）；一次汇总全部问题，Luna统一返修，完成现有脚本的保存读回后才进入下一批。Luna负责执行，主控负责方案和协调。
计数按公司处理结果，包含已保存、部分填写和真实阻塞，不按“成功保存10家”计数。单任务、名单本来不足10家的尾批或用户叫停时，对实际范围统一审查后结束；尚有未处理公司时，不能因某家新站点、刚修脚本或提前保存成功而逐家启动审查。
本批填写阶段固定运行版本；问题先加入批次清单，批末集中修复。代码提交仅作恢复点，不触发打包、安装或发布。集中修复使用同一个开发候选版本验证；本批closed后，确需分发才统一打包、安装、发布一次，下一批再使用新版本。
批次完成表示可执行修复已结束、其余项已有明确阻塞和结果记录；不代表所有公司均已保存或已提交。详细交接字段见 [批次清单与恢复](references/evidence-recovery.md#独立审查清单与恢复)。

## 1. 核对任务与资料

### 1.1 读取已有状态

1. 运行 `python3 skills/recruitment-link/scripts/table-locations.py --data-root <dataRoot> show`，先确认第一张来源表与第二张结果表。按 [表格筛选与收尾](../recruitment-link/references/fill-selection.md) 读取当前表格，生成允许填写的行清单。
2. 只为清单中的 eligible 行查找已关联 taskId/runId，再用 `apply.get_status { runId }` 读状态。task list 用于查关联记录，不根据最近运行时间、历史登录成功或旧失败清单选择公司。
3. 按 [私有资料](references/private-resume-data.md) 读取当前行绑定的简历、履历和答案。没有可用中文简历时索要；先应用最新信息和暂填授权。必填和选填栏目都补充；已获“先写并标记”授权的不确定项，按现有资料先拟写或匹配最接近选项并记录；真实证明材料与本人验证缺失单独登记。
4. 没有第二张表时先按登记/创建流程补齐结果存放位置；不把“以后有推荐岗位再建表”作为省略保存结果的理由。

### 1.2 确认可以继续

1. 本批仅处理未投递记录时，跳过已确认提交的任务；结果不确定的任务先核对官网应聘记录，保持原结果，不能当未投递重做。
2. 明确岗位须确认官网仍接受申请、硬条件与用户事实相符；停止招聘或明确不符就记录原因。公司简历入口本身不能证明岗位开放。
3. 没有有效运行或登录已失效，交给 [登录流程](../recruitment-session/SKILL.md)，取得可用 `runId` 后继续。缺少具体岗位不妨碍独立站内简历的填写。

收到用户新信息，先执行 [资料与偏好更新](../recruitment-capability-evolution/SKILL.md#用户提供最新信息时)，再清除对应旧阻塞。 新资料影响的字段即使已有内容也必须核对；使用当前解析出的路径局部返修。官网有精确匹配选项时直接采用；只有缺少精确项时才选近似项，并立即记录到表格供用户核验。

## 2. 读取真实字段并补答案

### 2.1 扫描和解析

已在简历页时直接调用 `apply.resolve_page { runId }`，它会读取页面并解析答案。只有需要查入口、控件或补证据时调用 `apply.inspect_page`。
外层 `ok: true` 只说明工具调用成功。网站脚本分支检查 `data.preparation.missing/conflicts/skipped` 和缺失材料/记录；通用分支检查 `data.missing`、`data.requiresReviewRuntimeRefs`。
大量填写前先核实必填上传项是否有对应真实材料。缺少成绩单、证书等文件时，先确认官网是否支持不带材料保存草稿；不支持则记录具体材料阻塞，转本批下一家公司，不先完成大量无法保存的字段。
工具返回空页面、无字段或找不到下一步时，先按 [入口与页面恢复](../recruitment-link/references/entry-recovery.md) 检查实际页面，按结果回到来源查找、视觉操作或能力演进；再继续解析。
`apply.resolve_page` 两条路径都返回 `source.payload`，即本任务已合并的完整资料，包含有效履历回答和项目排除结果；填写与审查复用它。`resolvedKeys` 只有键名，不能据此声称字段内容正确。先应用用户的选项映射和暂填授权；确定事实冲突才停止对应字段，已授权近似选项不要反复追问。

### 2.2 保存用户回答

收到真实回答后调用 `apply.save_answers { runId, answers: [{ canonicalKey, value, scope }] }`，scope 按私有资料说明选择。
拿不准的匹配一个近似项，然后立刻记录到表格原有“不确定信息”列，供用户核验。按公司及时记录，不等整批结束；已确认的信息照常填写，不把暂填值记成真实资料。
随后再次 `apply.resolve_page { runId }`。新增履历或更换材料按私有资料说明更新任务绑定并建立新运行，旧运行不会自动读到新绑定。
必填缺项暂时无法补齐时记录该公司阻塞，先处理其他公司；同一问题在批次内合并询问。

## 3. 填写并检查当前表单

### 3.1 写入

以用户本次要求确定修改范围。补空任务保留已有内容；完整填写或修复任务同时修正与已确认资料冲突的旧值。正确字段直接沿用，有具体差异才写入。旧值没有来源且本次不改时标为沿用，不把核实全部历史字段变成本次的额外任务。选项匹配使用已确认偏好。
`apply.fill_page` 默认只补空项。Moka 和飞书脚本支持 `writeScope`：补空传 `{ "mode": "fill_missing" }`，按审查清单返修传 `{ "mode": "repair", "fields": ["resolve_page 返回的字段路径"] }`。先读 `apply.resolve_page` 返回的 `writeScope.fields`，只从这份清单选择路径；不能按网站数组位置猜重复记录。具体字段路径、保存前基线和失败处理见 [局部写入](references/scoped-write.md)。没有支持范围的脚本或通用页面会明确报错，不会静默整页覆盖。无适用脚本或结构化操作失败时，先按 [视觉操作](references/evidence-recovery.md#视觉操作) 使用 Computer Use。视觉路径仍失败时，再按 [能力演进](../recruitment-capability-evolution/SKILL.md) 在现有浏览器接口下补最小能力并验证；确实不能处理才停止该页，不调用整页脚本碰运气。
调用填写工具后检查 `data.outcome`、`data.fill.failed`、`data.preparation.skipped` 或实际字段读回；任务行筛选返回的 fillMode 只是写入范围要求，不是现有 MCP 参数。
官网分设工作与实习栏目时，同一段经历按已确认的任职性质只进入一个栏目；只有合并栏目时才统一填写，不能把一段实习复制到两栏。
官网解析附件后，先按来源核对每条教育、工作和项目的归属、标题与全文，修正解析产生的串位、伪条目和混合内容，再补空字段。解析成功只说明生成了表单，不说明分类和内容正确。
使用共用脚本批量填写时，复用整页保存读回；逐卡界面操作时才逐卡核对名称、日期、角色和全文，有差异只处理对应卡片。所有用户选中的项目逐条完整填写，沿用原名称、日期和角色；应用私有 `includeInApplications: false` 排除标记，不因名称含 Skill 等词自行删选。按实际栏目承载项目内容：默认将概述、详细条目和明确的职责内容完整放进项目描述，选填的“项目中职责”留空；只有一个叙述框时全部放在那里。官网将职责标为必填或用户明确要求分开时，再用资料明确的职责填写，缺少事实集中问。bullets 是条目排版，不代表职责，不按关键词拆分。
官网限制条数或字数时记录具体未填内容；未经用户允许，不通过合并项目或删掉后续段落消除错误。官网没有对应栏目时核实附件实际承载了哪些内容；附件存在不证明它包含后来补充的事实，未承载的信息如实记录。

### 3.2 校验与失败处理

调用 `apply.validate_page { runId }`。网站脚本检查 `data.validation.valid/issues`；通用分支检查 `data.valid/issues`。失败时只修有问题的字段，再校验。
结构化操作失败时，按 [视觉操作](references/evidence-recovery.md#视觉操作) 使用 Computer Use；有当前字段引用时可调用局部视觉辅助，验证提供完整 `expectedValue`，不能只验证非空。无字段引用不代表电脑操作不可用。
遇到浏览器/页面/字段操作/脚本/保存/读回等技术问题，宣布技术阻塞前必须先调用一次 [能力演进](../recruitment-capability-evolution/SKILL.md) 诊断和尝试修复；成功后继续原阶段，仍失败再记录具体阻塞。同一问题复用已有演进记录，不无限重复。缺用户事实或权限时不通过代码猜补或绕过。

## 4. 保存、重新打开与采集证据

填完后完成当前栏目和整页的保存/暂存，并重新打开确认内容仍在；不要停在仅填入未保存的状态。
自检通过后调用 `apply.advance { runId, actionKind: "save" }`。明确传 `save`，不用下一步或提交代替。
网站脚本分支检查 `data.saveDraft.attempted/saved`、`data.serverReadback.valid` 和 `data.evidencePath`；通用分支的 `data.saveConfirmation.confirmed` 只证明保存响应，仍须重新打开并读回。
保存失败或无法确认服务器读回时保留“保存/读回待核实”，不能报告完整成功。

每家公司首次处理结束后，交回已有的原始资料、实际填写范围、完整字段值、保存结果和必要截图，并更新本批 index。部分填写也必须登记；未保存的字段明确标为页面值，不伪装成服务器结果。没有进入简历的公司交回实际阻塞证据。
截图仅补文字不能确定的栏目归属、选中状态和附件；已有完整字段时不重复图片识字。多页或折叠卡片只补缺失范围。
将两表已经登记的“不确定信息”和用户允许的字段选择整理为对应字段的 `acceptedExceptions`，注明原表记录与原文；原始事实与暂填值分开。审查者直接按这些授权处理对应空值或暂填，不把整家公司全部字段豁免。
来源表和结果表按真实保存状态更新并读回；独审前不标记最终完成。保存、部分填写、无法保存分别保留，不为进入审查而重复保存。

## 5. 集中审查与返修

主控确认本批每家公司均已交回首次处理结果后，将完整 index、原始履历、preferences、两表不确定信息、各公司实际填写范围和证据一次交给 Sol；用户指定 Terra 时使用 Terra。提示词使用 [站内简历审查](../../agents/resume-field-reviewer.md)。填写者不负责审查结论。
本批所有公司都要有结论。部分填写审已填内容和停止原因；未登录只核实阻塞，不虚构一份待审简历。审查报告一次列全严格内容的错误、已接受例外、官网限制及真正缺证的具体字段，不按发现一个问题就退回一次。
报告齐全后进入 repairing。没有实际独立审查调用时保留 reviewing，不用填写自检替代。

Luna按同一份修复清单调用已有脚本或明确的局部操作，修复后保存并交回实际字段读回。修复预期值由初审清单提供；不能只用“操作成功”证明内容正确，也不新建万能验证程序。
复用已有脚本的保存读回能力确认清单项；保存涉及整份资料时，核实是否产生清单外变化。已核对且未变的内容沿用原结论，返修结果追加到原report.json，清单只更新阶段，不另建待审区、返修报告或整份逐字段报告。
默认不启动第二轮AI审查。仅有具体修复项读不到、保存结果矛盾、清单外内容发生变化或新增语义问题时，交原审查者处理这些具体项；不得扩成整份重新审查。仍无法确认的项记录真实阻塞，不能伪称修复完成。
仍有效的留空、暂填和自由选择授权，以及已核实官网限制，不作为返修理由；新确认事实按最新要求核对。已确认的项目、实习、工作、学历、日期和数字出现差异，仍须修复。
全部修复项已确认或有明确无法继续的证据，且两表结果同步后，本批才标 closed；之后方可派下一批。

## 6. 结束或交接

本批初审及必要返修结束后，按表格筛选与收尾第 3 节更新第二张表的同一行；确认完整且审查与修复结果齐全、结果表写回成功后，才勾选第一张表的处理完成并读回。写回失败记“表格待同步”，不能宣布该公司已全部完成。全部完成后运行 `node bin/applyctl.js task complete --task <taskId>`，使任务库与两张表保持一致；局部修复通过但整份仍有未完成项时保持原任务状态。
用户只要求填写时，本批保存、集中审查及必要返修结束后停止；有问题则如实交付未完成项。用户授权找岗位时，按 [候选岗位记录](../official-apply/references/source-and-candidate-records.md) 收集岗位链接和完整 JD，交用户选择。
用户明确要求真实投递时，将 `taskId`、`runId`、`serverReadback`、`evidencePath` 和通过的独审报告交给 `job-application-submit`；岗位专属字段改动也须先审查。
无需立即交接到下一阶段时，完成证据采集后调用 `apply.close_run { runId }` 释放本次会话；需要修复时重新打开。批次用 `apply.next_work { batchId }` 继续；若重复返回同一已知阻塞项，按登录流程第 2.2 步从本批清单继续其他任务。结束或报告整批等待前，把尾批待审记录审完。
