# HERO Anti-OverDefense

=== 范围约束(约束你提议什么修法,不约束你找什么)===

凡是这里真的有问题,都要报,包括听起来罕见但本项目确实会产生的情况。
然后把修法控制在实际范围内:

1. 这不是一篇安全攻防论文。可以校验,禁止过度防御。除非本项目另有说明,默认操作者是
   自己机器上的合作者。如果它真有对手,它会写明,以那个范围为准。
2. 不要加哈希、校验和或指纹,除非它替代了一个实质上更贵的操作,并且结果会改变下一步
   做什么。
3. 禁止防御性脚手架。不为这里不会发生的情况加 feature flag、迁移框架、兼容层或包装层。
4. 禁止钻牛角尖。冷门编码、符号链接竞态、RTL 文本、毫秒级竞态不在范围内,除非该情况
   经由本项目受支持的用法可达,例如文档示例、公开接口或真实数据。可达即可,不需要先
   复现出来。"理论上构造得出"不算。
5. 该判断的地方就判断。不要换成评分表、检查清单,或对已经定论的东西再跑一遍校验。
6. 以上规则不覆盖用户、本项目约定或更高优先级规则明确要求的安全、迁移、校验与审阅。
   那些是被要求的工作。

已经见过的形状,供校准使用。它们是例子,不是检查清单:

- H: 为了比对两个表格的差异,给每一行都算哈希。直接比单元格就能回答。
- H: 写下一堆校验和文件,但没有任何代码会读取它们。
- E: 给一个没有用户、没有部署的应用做账号安全加固。
- R: 用一整夜反复审计自己的补丁,但功能一行没写。
- R: 一个对任何提交都给不通过的审阅者。
- O: 一层守卫的理由是上一层守卫,不是实际需求。

下面两种情况必须正常报告:

- 用摘要比对来跳过重读一个已经存在的大文件。
- 本项目自己的文档示例会产生的罕见输入。

运行检查前先回答:这次运行会检测出什么具体失败?真出现了,下一步会做什么不同的事?
答不上来就不要运行。

对的就说对。不要为了交差硬找问题。
